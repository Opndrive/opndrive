[x] 4. #82 - useSearch violates the Rules of Hooks
        https://github.com/Opndrive/opndrive/issues/82
        Labels: bug, priority: high, search, state-management

        DONE - traced the actual trigger first, per the TODO below, and it
        does NOT match the issue as literally written: AuthProvider renders a
        loading placeholder instead of children while isLoading is true, and
        every path that sets apiS3 sets userCreds in the same synchronous
        continuation (React batches them), so a mounted SearchPage/SearchBar
        instance never actually sees apiS3 flip mid-life under the current
        code. The real risk is that LayoutShell's gate (layout.tsx) checks
        isLoading + userCreds but NOT apiS3 - the two are only in sync by
        convention across auth-context.tsx and use-auth-guard.tsx, not by any
        enforced invariant, so the crash is one refactor away rather than
        currently firing. Fixed anyway since conditional hooks are unsafe
        regardless of whether today's callers happen to avoid it.
        Removed the early return; searchService is now memoized with
        useMemo(apiS3) instead of rebuilt every render (this also fixes a
        second, always-active bug: it sat in search's own useCallback deps,
        so search was rebuilt every render and memoization did nothing).
        Every exposed function now guards on searchService being null instead
        of the hook returning a differently-shaped object - one return shape,
        always.
        Added vitest + @testing-library/react + jsdom to frontend (previously
        zero test infra there) specifically to catch this class of bug, since
        it's a React runtime invariant that a logic-only test can't see.
        Proved the test has teeth: reverted to the old early-return shape and
        got the actual React errors ("Rendered fewer hooks than expected" /
        "Rendered more hooks than during the previous render") on both
        transition directions (null->apiS3 and apiS3->null). Restored the fix,
        reran clean. Typecheck, eslint, and next build all pass.

        POST-REVIEW (paranoid pass found 5 real problems, all fixed):
        a) My "eslint passes" claim was hollow - eslint-plugin-react-hooks was
           NOT installed at all. Proved it by linting a textbook conditional
           useCallback: exit 0. Installed and wired it. It immediately found
           62 rules-of-hooks errors in 15 OTHER files - #82 was one instance
           of a systemic pattern, not a one-off. Filed #105 with the full list.
           Enabling it as a hard error broke `next build` (exit 1), so it is
           now error globally + warn for the 15 known-debt files. That is a
           ratchet not an amnesty: lint-staged runs --max-warnings=0, so
           touching a debt file still forces a fix, and no new file can join
           the list. Verified both directions.
        b) My null guard traded a loud crash for a silent lie: with no
           provider, search() no-ops and the page renders "No results found"
           for a query that never ran - and page.tsx's effect keyed on [query]
           alone would never retry once apiS3 arrived. Added isReady, gated
           the effect on it, and gave both the page and the search bar a
           distinct "Connecting to your storage..." state.
        c) In-flight searches were never aborted on unmount - the service kept
           paginating (100k ceiling) for a dead component and its results
           landed in the module-level store afterwards. These are billed S3
           requests. Added a cleanup that aborts and resets the shared loading
           flag (which outlives the component, so skipping it would strand the
           next mount on a permanent spinner).
        d) The finally block cleared shared state unconditionally, so a
           superseded search would discard the controller of the search that
           replaced it - killing the Cancel button and hiding the spinner
           mid-search. Now keyed to the controller it started with.
        e) `globals: true` without a matching type reference meant an
           idiomatic globals-style test would pass `pnpm test` and then break
           `next build`. Added vitest-env.d.ts (a reference file, NOT
           compilerOptions.types, which would have switched off auto-inclusion
           of @types/node and friends).
        Tests 2 -> 9. Proved teeth by reverting each fix separately: memoisation
        (2 fail), unmount abort (1), finally race (1), isReady (1). One test
        was TOOTHLESS on first write - "does not touch store state" passed even
        with the guard removed, because the error path happened to reset the
        same state. Rewrote it to count store transitions instead of asserting
        on final state; it now fails with "expected 4 to be +0".
        Also caught a mock artifact: my useNotification mock minted a fresh
        vi.fn() per render, failing the memoisation assertion for a reason that
        does not exist in production (the real one is useCallback-stable).
        Follow-ups filed: #104 (search cache survives logout - leaks results
        across AWS accounts, reachable TODAY and arguably worse than #82),
        #105 (the 62 violations), #106 (store over-subscription).
